# 当前运行结果、已知问题与待反馈事项

> 用途：可将本文件连同仓库代码直接发送给网页 GPT 审阅。本文只报告已实际运行的第一问结果；不把无标签目标域 A–P 的候选分类当作真值。

## 1. 当前目标与代码入口

项目处理滚动轴承故障迁移诊断问题。当前优先完成第一问：选择和审计后续可用的源域数据、分析故障机理、建立文件级 metadata，并形成可供第二问/第三问使用的标准特征数据集。

当前主入口：

```powershell
python .\src\q1_pipeline.py
```

核心实现位于 `src/q1_pipeline.py`，输出位于 `outputs/q1/`。`bearing_mvp.py` 和 `dann_feature_baseline.py` 是早期诊断基线，不是当前第一问结论来源。

## 3. 已实现的内容与可核查产物

- `data_audit.csv` / `data_audit_summary.json`：每个 MAT 文件的审计结果和分支统计；
- `source_metadata.csv`：正式源域文件级标签、转速、载荷、故障尺寸/位置等 metadata；
- `features_source_raw.csv`：完整窗口级特征；
- `features_source_selected.csv`：去除近零方差和高相关冗余后的 28 维特征；
- `feature_quality.csv`：方差、文件内窗口变异系数、辅助互信息和筛选理由；
- `source_domain_selection.csv`：候选源域诊断；
- `figures/`：多模态故障机理图、包络阶次图、特征相关图、文件级 PCA 图（PNG/SVG/PDF/TIFF）。

TIFF 是为论文排版保留的本地无损导出，其中一张约 155 MB，超过 GitHub 单文件 100 MB 限制；仓库上传 PNG/SVG/PDF，TIFF 可随时由主脚本在本地重新生成。

受控 16 文件子集仍保留，但仅用于故障机理的可解释展示，不再作为正式源域训练集，以避免固定故障尺寸和外圈位置造成过于容易的验证任务。

## 4. 旧基线揭示的问题（不是当前分类结论）

早期 `bearing_mvp.py` 在受控 16 文件 DE 子集上获得文件级 Macro-F1=1.000，而将对应流程换为 FE 子集时约为 0.818。该差异只能说明受控 CWRU 子集内的可区分性，不可外推为列车目标域的泛化能力。

早期无监督候选结果也不稳定：source-only 将 A–P 全部偏向 N，且 16/16 均被 OOD 标记；CORAL 与 source-only 在 9/16 文件上不一致；DANN 12 轮与 50 轮候选仅 7/16 一致。因此当前第一问明确不输出 A–P 分类、CORAL 或 DANN 的任何结论。

## 5. 不能宣称的结论

- 不能报告 A–P 的“准确率”或把任一候选类写成真值；
- 不能把 MMD/PAD 下降、PCA/t-SNE/UMAP 分布、置信度或伪标签一致性当作目标诊断正确的证据；
- 目标轴承几何未知，不能把其频谱峰强行命名为 BPFO/BPFI/BSF；
- 重叠窗口不是独立样本，不能随机按窗口切分训练/测试，或按窗口数报告泛化能力；
- 不能仅因 MMD 较小就说 12k_FE 比 48k_DE 更适合作为正式源域。

## 6. 希望网页 GPT 重点审阅和反馈的问题

1. 在目标域无真值的前提下，第二问应如何设计**文件级、无泄漏**的验证与模型选择，才能避免用伪标签自证？
2. 源域选择除当前 MMD/PAD、测点、标签覆盖、带宽外，还应加入哪些可复现且不使用目标标签的量化证据？如何设定权重或决策规则？
3. 正式源域的类别文件数不平衡（N=4、B=12、IR=12、OR=28）。后续训练与文件级评估应怎样使用 class weight、分组交叉验证和消融，才不会夸大结果？
4. 目标转速只知题设名义值、没有瞬时转速。当前采用阶次特征和固定时间窗，是否需要改成约 5/10/15 转覆盖的窗口长度灵敏度分析？合理表述边界是什么？
5. 第一问还应补充哪些机理图、统计检验、文件级稳定性或特征鲁棒性分析，才能使“源域选择与特征构建”更有说服力？
6. CORAL/DANN 在什么前提和何种消融验证完成后，才适合进入第三问？如何防止类别塌缩和错误伪标签的循环放大？
